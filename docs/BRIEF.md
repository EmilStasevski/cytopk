**Interpretation of the owner's note ("iv … in general form").** The owner wrote "do iv a little in general form". Assumption: **IV = intravenous administration**, and "general form" = build a *general* compartmental PK/PD framework whose v0 scope is IV dosing (bolus and infusion), designed so that oral/subcutaneous absorption, other elimination types and covariates can be added later. **The idea in one paragraph.** One repo with two Rust components and one story:
1. `cytopk-fcs`: a robust, fast FCS 3.0/3.1 reader (and a small writer) that outputs tidy tables (Arrow/Parquet/NumPy), plus simple transforms, compensation, rectangular/polygon gating and per-sample summaries (event counts in gates, medians).
2. `cytopk-sim`: a general ODE-based PK/PD simulator (IV bolus/infusion; 1- and 2-compartment; linear and Michaelis-Menten elimination; indirect-response PD that drives an immune-cell population), batch-parallel with Rayon, deterministic, exposed to Python via PyO3 + maturin as NumPy arrays.

Known ground truth makes this testable and avoids any data-licence or patient-data issues.

**Scientific disclaimer to keep in the README:** research prototype, toy models with illustrative parameter values, not validated for clinical or regulatory use. No real patient data anywhere in the repo.

**Non-goals (v0):** GUI, full gating GUI/auto-gating, regulatory-grade (GxP) validation, oral/SC absorption (design for it, don't build it), stiff-solver zoo, GPU code in Rust.

## 4. Component A: `cytopk-fcs`

### 4.1 Scope (v0)
- Read FCS **3.0 and 3.1** (tolerate 2.0 if cheap; reject others with a clear error). List mode (`$MODE = L`) only.
- Data types: `$DATATYPE` = `F` (f32), `D` (f64), `I` (unsigned ints with per-parameter bit widths `$PnB`, masked by range `$PnR`); `A` (ASCII) only if trivial, else error "unsupported".
- Byte order: `$BYTEORD` = `1,2,3,4` (little-endian) or `4,3,2,1` (big-endian); error on other orders (or support if trivial).
- Multiple datasets per file via `$NEXTDATA`.
- Output: `FcsFile { header, text: BTreeMap<String,String> (keys normalised to upper-case, `$` prefix kept), channels: Vec<Channel>, data: events × params (f32 or f64), analysis: Option<Vec<u8>> }`.
- **Writer**: write a valid FCS 3.1 (float32, little-endian, list mode) from `Vec<Channel>` + matrix + optional keywords. Needed for synthetic fixtures and round-trip tests.
- Utilities: arcsinh transform (cofactor parameter; typical ~150 for fluorescence flow, ~5 for mass cytometry; make it a parameter, state the default in docs), compensation via the file's spillover matrix, rectangular and polygon gates (TOML config), per-sample summaries (events total, events in gate, median/percentiles per channel).
- Stretch: logicle/biexponential transform (Parks, Roederer & Moore, 2006), validated against FlowKit or flowCore output.

### 4.2 Format facts to implement carefully (verify against the FCS 3.1 spec, Spidlen et al. 2010, *Cytometry A*; the spec is the authority, the list below is a checklist, not a substitute)
- **HEADER** (first 58 bytes): bytes 0–5 version string (`FCS3.1`), 6–9 spaces, then six 8-byte ASCII integers (right-justified, space padded): TEXT begin/end, DATA begin/end, ANALYSIS begin/end (byte offsets, inclusive end). If a segment is beyond the header's 8-digit limit, the header field is `0` and the real offsets are in `$BEGINDATA/$ENDDATA`, `$BEGINANALYSIS/$ENDANALYSIS`, etc. Offsets in TEXT keywords take precedence when header fields are 0.
- **TEXT segment**: the first byte is the delimiter; keyword/value pairs alternate; a delimiter inside a value is escaped by doubling it; empty values and leading/trailing delimiter quirks occur in real files, so be lenient in `Lenient` mode and strict in `Strict` mode. Keywords are case-insensitive in practice (normalise on read, but preserve original in `raw_text`). Encoding: treat as UTF-8 with Latin-1 fallback.
- **Required keywords to read**: `$TOT`, `$PAR`, `$DATATYPE`, `$BYTEORD`, `$MODE`, `$NEXTDATA`, and per parameter `$PnN` (short name), `$PnB` (bits), `$PnR` (range), `$PnE` (log amplification `f1,f2`; `0,0` = linear), plus optional `$PnS` (long name/stain), `$PnG` (gain; not for F/D), `$PnV`, `$CYT`, `$DATE`, `$FIL`, `$SPILLOVER` (3.1), `$SPILL`/`$COMP` (non-standard/3.0 variants).
- **DATA segment**: list mode is event-major (all parameters of event 1, then event 2…). Size check: bytes must equal `$TOT × Σ(bits/8)`; real files often violate this (off-by-one in `$ENDDATA`, wrong `$TOT`). Strict: error. Lenient: warn, trust `$TOT` and available bytes, report in `warnings`.
- **Integer data**: apply the `$PnR` mask/range; decide and document whether to scale (usually values are used as stored; log-amplified `$PnE` channels need conversion `10^(f1 * x / range)`-style, so read the spec section before implementing, and test on a file that has `$PnE != 0,0`; if no such file is available, implement as documented and mark "untested on real data").
- **Compensation**: read matrix from `$SPILLOVER` (3.1: first value N, then N channel names, then N×N values). Define clearly what rows/columns mean and whether you invert; validate your result against FlowKit or flowCore on a real compensated file before trusting it. Document the convention in `docs/fcs_notes.md`.
- **Never trust sizes from the file for allocation** without an upper bound (guard against files claiming 10^12 events).

### 4.3 Implementation guidance
- Hand-rolled byte parsing with `u32::from_le_bytes`-style conversions (or `byteorder`); `memmap2` for large files with an `Read`-based fallback. Parse TEXT with a manual scanner, not regex.
- Convert to a column-major layout on request (`events × params` row-major is the file layout; analysis usually wants per-channel columns). Provide both views without double-copying where possible.
- Arrow/Parquet via the `arrow` and `parquet` crates (check current maintained crates; avoid deprecated ones). Provide `FcsFile::to_record_batch()`.
- Parallel multi-file reading with Rayon (`read_many(paths) -> Vec<Result<FcsFile,_>>`).
- Error type with offsets and keyword names in messages; collect `warnings: Vec<FcsWarning>` instead of printing.
- Fuzz: `proptest` for round-trip (`write → read → equal`), and `cargo-fuzz` (or proptest with random byte mutation) for "no panics".

### 4.4 Tests (must exist)
1. Round trip: random matrices, channel counts 1–40, events 0–10^5 ⇒ write ⇒ read ⇒ bit-identical (f32) and keyword-identical.
2. Delimiter escaping: values containing the delimiter, empty values, unusual delimiters (`/`, `|`, `\x0c`).
3. Big-endian and little-endian; `F`, `D`, `I` (including mixed `$PnB` such as 16 and 32 bits).
4. Offset edge cases: header offsets 0 with `$BEGINDATA/$ENDDATA`; off-by-one `$ENDDATA`; wrong `$TOT`; truncated data; truncated TEXT.
5. Multiple datasets (`$NEXTDATA`).
6. Cross-check against independent readers on real public files (pytest, Python side): `flowio` / `fcsparser` / `FlowKit` (choose what installs cleanly; any one or two is enough). Compare channel names, event counts, and the data matrix (allclose; exactly equal for float32).
7. Adversarial: random byte flips and truncations never panic.

## 5. Component B: `cytopk-sim`

### 5.1 Design: "general form", v0 scope IV
Core abstractions (sketch; adapt as needed):

```rust
pub trait Model: Send + Sync {
    fn name(&self) -> &'static str;
    fn n_states(&self) -> usize;
    fn param_names(&self) -> &'static [&'static str];
    fn init(&self, theta: &[f64], y0: &mut [f64]);                  // baseline state
    fn rhs(&self, t: f64, y: &[f64], theta: &[f64], input: &[f64], dy: &mut [f64]); // input = infusion rates per state
    fn observe(&self, y: &[f64], theta: &[f64], out: &mut [f64]);   // e.g. concentration, response
    fn n_outputs(&self) -> usize;
    fn analytic(&self) -> Option<&dyn Analytic> { None }            // closed form where it exists
}

pub struct Dose { pub time: f64, pub amount: f64, pub state: usize, pub duration: Option<f64> } // None = bolus; infusion rate = amount/duration
pub struct Schedule { pub doses: Vec<Dose> }                         // sorted, validated

pub fn simulate_batch<M: Model>(m: &M, thetas: ArrayView2<f64>, sched: &Schedule,
                                times: &[f64], opts: &SolverOpts) -> Array3<f64>; // N × T × n_outputs
```

- Use **static dispatch** inside `simulate_batch` (generics), and a `match` on the model name at the PyO3 boundary.
- **Dosing/events**: integrate segment by segment between event times (dose times, infusion end times, requested output times). Bolus adds `amount` to the target state instantly; infusion adds a constant input rate on `[t, t+duration)`. Never let the adaptive step cross a discontinuity.
- **Solvers**: implement (a) fixed-step RK4 (for reference/debug), (b) adaptive Dormand–Prince RK45 with `rtol`/`atol` and dense or segment-end output (output at requested times by stepping exactly to them, or by dense output; document the choice). Optionally compare with an existing Rust ODE crate (`ode_solvers`, `diffsol`; check current status) as a dev-dependency or benchmark baseline, not as a required dependency. Add a stiffness note in `docs/models.md`; do not build an implicit solver in v0.
- **Parallelism**: Rayon `par_iter` over simulations; each simulation writes into a disjoint slice of a pre-allocated output buffer. No locks in the hot loop. Pre-allocate per-thread scratch buffers (`map_init`).
- **Noise/observation models (separate stage, seeded)**: optional functions `add_lognormal_noise`, `sample_beta_binomial`, using `rand` + `rand_chacha`/`rand_pcg`, **one RNG stream per simulation index** derived from `(global_seed, index)` with a proper seed-mixing function, so results do not depend on thread scheduling.
- **Covariates (optional, small)**: allometric scaling example `CL_i = CL_pop·(WT_i/70)^0.75`, `V_i = V_pop·(WT_i/70)`, implemented as a pre-processing function that maps (population params, covariates) → individual params.

### 5.2 Models for v0 (all with units documented; time in days, amounts in mg, volumes in L, concentrations in mg/L)
| id | description | states | params |
|---|---|---|---|
| `onecmt_iv` | 1-compartment, linear elimination | A1 | CL, V |
| `twocmt_iv` | 2-compartment, linear elimination | A1, A2 | CL, V1, Q, V2 |
| `twocmt_mm_iv` | 2-compartment, Michaelis–Menten elimination (nonlinear) | A1, A2 | Vmax, Km, V1, Q, V2 |
| `twocmt_iv_idr` | `twocmt_iv` + indirect-response PD: drug *stimulates* production of activated immune cells | A1, A2, R | CL, V1, Q, V2, kout, Emax, EC50 |

**PD sub-model for `twocmt_iv_idr`** (illustrative, normalised; state this clearly in docs):
`C = A1 / V1`;  `dR/dt = kout · (1 + Emax · C / (EC50 + C)) − kout · R`,  `R(0) = 1` (baseline normalised to 1, so production rate at baseline equals `kout`).
Observed activated-cell fraction: `p = R / (R + 9)` so the baseline fraction is 10 % (`R_ref = 9·R0` fixed, document it; the numbers are a toy choice).
Observations per subject and time: `PK: log C_obs ~ Normal(log C, σ_pk)`; `PD: y_gate ~ BetaBinomial(n_events, p·φ, (1−p)·φ)` where `n_events` = events in the parent gate and `φ` controls overdispersion.
Illustrative prior ranges (log-normal around these; typical of a monoclonal-antibody-like drug, but only for demonstration): CL ≈ 0.2 L/day, V1 ≈ 3 L, Q ≈ 0.5 L/day, V2 ≈ 3 L, kout ≈ 0.3 1/day, Emax ≈ 2, EC50 ≈ 5 mg/L; doses e.g. 50/200/800 mg as 1-hour infusions. Put the table in `docs/models.md`.

**Closed forms (used as test oracles and as the NumPy baseline):**
- 1-cmt bolus: `C(t) = (D/V) e^{−k t}`, `k = CL/V`.
- 1-cmt infusion (rate `R0 = D/T_inf`): during infusion `C(t) = R0/(CL) (1 − e^{−k t})`; afterwards `C(t) = C(T_inf) e^{−k (t−T_inf)}`.
- 2-cmt: derive bi-exponential `A e^{−αt} + B e^{−βt}` from micro-constants (`k10 = CL/V1`, `k12 = Q/V1`, `k21 = Q/V2`; `α, β` roots of `s² − (k10+k12+k21)s + k10·k21 = 0`). Write the derivation in `docs/models.md` and verify against numerical integration.
- Superposition for multiple doses of linear models; steady-state accumulation ratio `1/(1 − e^{−kτ})` for 1-cmt bolus every τ.

### 5.3 Tests (must exist)
1. Numerical vs analytic: 1-cmt and 2-cmt, bolus and infusion, ≥ 1000 random parameter sets (log-uniform within the prior ranges); max relative error ≤ 1e-6 at `rtol=1e-8, atol=1e-12` (tune and log in `decisions.md`).
2. Conservation: with `CL=0` total amount `A1+A2` is constant; with elimination, `Dose − eliminated − A1 − A2 = 0` (add an "eliminated amount" auxiliary state in a test model).
3. `AUC_{0..∞} = Dose/CL` (numerical trapezoid with fine grid or an auxiliary AUC state).
4. Non-negativity of amounts; monotone decay after a bolus (1-cmt); `R` bounded below by 0.
5. Property tests (`proptest`): sorted/unsorted dose lists validated; infusion with `duration → 0` approaches bolus; scaling dose scales linear-model amounts linearly but not MM-model amounts.
6. Determinism: result identical for 1, 2, and all threads; identical across two runs with same seed; different seeds ⇒ different noise.
7. Discontinuities: a dose at time exactly equal to an output time (convention: the output at time `t` includes the dose given at `t`; document it).
8. Optional cross-check with R (`mrgsolve` or `rxode2`) or Python `scipy.integrate.solve_ivp` at tight tolerances on 3–5 reference scenarios; store the reference arrays as small `.npz`/`.json` fixtures generated by a committed script.

## 7. Benchmarks: comparison with the common Python tools

**Principle:** answer "when is this worth it?" not "Rust is fast". Equal accuracy, equal outputs, warm and cold timings, scaling curves.

### 7.1 Simulation baselines (same models, same dose schedule, same output times)
| baseline | notes |
|---|---|
| NumPy closed form, vectorised over N | only linear models (1- and 2-cmt); likely the hardest baseline to beat, so include it |
| SciPy `solve_ivp` (RK45; also LSODA/Radau) in a Python loop | the typical "I just call SciPy" path; use `t_eval`, same `rtol/atol` |
| SciPy `odeint` (LSODA) in a loop | legacy but common |
| Numba `@njit` custom RK4/Dormand–Prince (+ `prange`) | fair JIT competitor; report compile time separately |
| JAX + diffrax, `jit` + `vmap` (CPU; GPU if available) | modern ABI-friendly competitor; report compile time and steady-state separately; note float64 must be enabled for equal accuracy |
| optional: R `rxode2` / `mrgsolve` | the pharmacometrics reference tools; compare per-simulation single-thread speed via a subprocess; skip if R is not installed |
| optional: `torchdiffeq` | only if cheap to add |

**Matrix:** model ∈ {`onecmt_iv`, `twocmt_iv`, `twocmt_mm_iv`, `twocmt_iv_idr`}; N ∈ {10³, 10⁴, 10⁵, 10⁶}; T ∈ {10, 50} output times; multiple-dose schedule (e.g. weekly ×4); threads ∈ {1, 2, 4, 8, all} for parallel implementations. **Equal accuracy:** use `rtol=1e-6`, `atol=1e-9` for all adaptive solvers, and *measure* the max relative error against the analytic solution (or a tight-tolerance reference for nonlinear models) and put it in the result table next to the time. If a tool cannot reach the accuracy, say so.

**Metrics:** wall time (median and IQR of ≥ 10 repeats after warm-up), simulations per second, speed-up vs SciPy loop and vs best baseline, peak RSS, cold-start overhead (import + first call, JIT compile), end-to-end "time to produce a 10⁶-simulation training set as a float32 NumPy array" including conversion.

### 7.2 FCS baselines
Compare against `flowio`, `fcsparser`, `FlowKit` (and R `flowCore` if available) on: (a) a single file, sizes ≈ 10⁵, 10⁶, 10⁷ events × 20 and 40 parameters (generate with your writer, since size scaling needs files you control, plus 1–2 real public files for sanity); (b) 100–1000 small files read in parallel; metrics: time to a NumPy `float32` matrix, peak RSS, correctness (identical data). **Expect modest differences for the data segment**: Python readers typically use `numpy.frombuffer`, so they are already close to memory bandwidth; the plausible Rust advantages are TEXT parsing, many-file parallelism without the GIL, lower memory via mmap, and robust error reporting. Report whatever you find.

- Script everything (`benchmarks/bench_*.py`), run on an otherwise idle machine, pin library versions in `requirements.lock`, record `lscpu`/CPU model, RAM, OS, Python/Rust versions, and commit SHA in the result JSON.
- Output: CSV + JSON in `benchmarks/results/`, plots in `benchmarks/results/*.png` (use the `dataviz` skill if available: consistent colours, labelled axes with units, log-scale where appropriate, one message per figure).
- `docs/benchmarks.md` states the conclusions in plain words, including *where Rust is not worth it* (for example if NumPy closed form wins for linear models, or JAX on GPU wins for huge N), and *where it is* (nonlinear models with events on CPU, no JIT warm-up, deterministic seeding, small deployment footprint, many-file ingestion).

## 8. End-to-end example (the "unification")

`examples/03_end_to_end_sbi_bayesflow.ipynb` (and a plain `.py` version that runs headless):

1. **Design:** 3 dose levels × 8 subjects (individual-level inference per subject in v0), sampling days e.g. `[0.04, 0.5, 1, 2, 4, 7, 14, 21, 28]`, 1-hour infusion at day 0.
2. **Prior predictive check** (ties to prior specification): sample parameters from the priors, simulate `twocmt_iv_idr`, plot PK and activated-fraction envelopes against plausible ranges; show one case where a too-vague prior gives absurd curves.
3. **Ground-truth data:** draw "true" parameters, simulate `C(t)` and `p(t)`, add PK noise; for each subject and time create a synthetic cell sample: `n_total` events in 6–10 channels, with a **mixture of Gaussians on the arcsinh scale**: fraction `p` "activated" (e.g. CD69-high) vs `1−p`, plus debris/other populations; write as FCS with `cytopk.write_fcs`.
4. **Read → gate → count:** read the FCS files with `cytopk.read_fcs_many`, transform (arcsinh), apply gates from a TOML file, obtain `(n_events_in_parent_gate, n_activated)` per sample. Verify these counts agree with what the generator intended (they will differ by sampling noise, which is exactly what the beta-binomial observation model describes).
5. **Amortized inference:** with BayesFlow 2.x, define prior + simulator (`cytopk.simulate` + noise functions, batched), train an amortized posterior (e.g. a coupling-flow or flow-matching network with a suitable summary network for the time series; choose what the current BayesFlow docs recommend), using online training if the simulator can be called in batches, otherwise offline datasets generated up front. Use the JAX or PyTorch backend, whichever installs cleanly. Record training time and the share of it spent in simulation (this is where the Rust speed matters or doesn't).
6. **Validation:** simulation-based calibration / rank-ECDF plots, posterior contraction and z-scores for each parameter, and posterior predictive checks against the gate counts and PK values; apply the trained network to the *parsed FCS summaries*, and compare recovered parameters to the known truth.
7. **Stretch (only after v0):** (i) population-level model with set-based summary networks across subjects (multilevel structure, inter-individual variability `η_i ~ N(0, Ω)`); (ii) amortized model comparison between `onecmt_iv_idr` vs `twocmt_iv_idr`; (iii) compare amortized posteriors to a Stan/NUTS fit of the same individual model for a few subjects.
