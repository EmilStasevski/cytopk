## 2026-11-06: M1 simulator design
- **Outputs come from stepping exactly to each output time**, not from dense output. Output accuracy then equals the
  solver's controlled accuracy, and no step crosses a discontinuity, because dose times and infusion ends are also
  breakpoints. The cost is shorter steps on dense output grids. This can be revisited in M4 if benchmarks show it matters.
- **Simulation starts at t = 0** from `Model::init` (zeros for PK). Dose and output times must be ≥ 0. Doses after
  the last output time are dropped from the integration plan.
- **Event convention:** the output at `t` includes boluses at `t`. Infusions are active on `[start, start + duration)`. Infusion
  rates for each piece are recomputed from the schedule at every breakpoint instead of being added and subtracted, so no
  rounding error builds up.
- **Step size across pieces:** the last unclamped proposal is carried over. A step clamped to a piece end does not shrink
  it. The first stage is re-evaluated at each piece start because the RHS can jump. The Hairer starting-step heuristic runs once
  per simulation, at the first piece.
- **No `Analytic` trait object** on `Model` (the brief sketches one). The closed forms are plain functions in `cytopk_sim::analytic`.
  They are only oracles and baselines, and keeping them off the trait means nonlinear models don't need a dummy implementation.
- **Parameter constraints are declared per model** (`Constraint::{Positive, NonNegative}`) and checked before integration.
  CL and Q may be 0, which the conservation tests need. Volumes must be > 0.
- **Batch errors are deterministic:** parameters are validated sequentially first, then solver errors are collected
  per row, and the lowest failing row index is reported (`SimError::InBatch`).
- **Accuracy target (brief 5.3.1):** at `rtol = 1e-8`, `atol = 1e-12`, the observed max relative error is 3.9e-8 (1-cmt) and
  2.3e-8 (2-cmt) over 1000 random sets each. The test asserts ≤ 1e-6 as the brief requests. Relative error is measured where
  `C > 1e-6·Cmax`. Below that, the error is measured relative to `Cmax` (observed ≤ 5e-14). This avoids dividing by values near
  zero long after the dose, where the absolute tolerance dominates by design.
- **Tests run with `opt-level = 2`**, so the 1000-set agreement tests take ~0.1 s.
- Test RNG: `rand_chacha::ChaCha8Rng` with fixed seeds, so the random parameter sets are reproducible across platforms.

## 2026-11-06: Go/no-go benchmark (before M2)
- **Script and results:** `benchmarks/quick_bench.py` → `benchmarks/results/quick_bench.{json,csv,md}` (git 772d522).
  The scenario is twocmt_iv with 4 weekly 1-hour infusions and 20 output times; every adaptive solver uses rtol 1e-6 / atol 1e-9.
  N = 1e4 and 1e5; 1 thread and all 16. This is a quick protocol (5–9 repeats, median), not the full M4 protocol.
- **Protocol choices:** each configuration runs in its own subprocess. On this hybrid CPU (i5-14400F: CPUs 0–11 are
  P-core threads, 12–15 are E-cores), single-thread rows are pinned to CPU 0 *before* any worker thread exists, so
  Rayon's and Numba's threads inherit the pinning. Unpinned single-thread runs varied by up to 1.5× depending on whether the
  scheduler picked a P- or an E-core (measured: 8.4 vs 13.1 µs/sim for the same Rust code). The SciPy loop is timed on the first
  2000 subjects (one run) and scaled linearly; the table marks this.
- **The Numba baseline is a line-by-line port of our Dormand–Prince** (same controller, same stopping points), so the
  speed comparison is like for like. Rust and Numba give bit-identical outputs.
- **First result: Rust was slower than Numba** (single thread, fixed θ: 8.3 vs 6.2 µs/sim). `perf` is not usable here (Ubuntu
  `perf_event_paranoid = 4`, kernel tools mismatch), so I attributed the time by controlled experiments
  (examples `step_stats`, `numba_port`):
  - Stepping to every output time costs 13 % of the per-simulation time (8.27 vs 7.21 µs with event-only stops; 60 vs 51 accepted steps,
    25 vs 9 segment restarts). Numba steps to the same times, so **this is not the cause of the gap**. After the fix it is 8 %
    (5.40 vs 4.99 µs).
  - Ruled out by measurement: `rhs` not inlined (forcing `#[inline(always)]` removed the calls but saved 0 %), the `0.0 +` seed in
    the stage sums (1 %), runtime state count / bounds checks (2 %), per-step bookkeeping (stats, budget, finite checks: 0 %),
    the library error norm (0 %), the Rayon batch harness (0 %).
  - A plain-Rust port of the Numba kernel took 5.8 µs, so the language was not the problem. **Cause:** the state and stage buffers were
    heap `Vec`s reached through pointers, so LLVM had to assume a store to one buffer could change another and reloaded values
    between stages. Moving the stage buffers alone to the stack gave 8.27 µs, moving `y` alone gave 8.03 µs, and moving both gave 5.44 µs.
  - **Fix:** fixed-capacity stack arrays (`MAX_STATES = 32`; capacity 4, 16 or 64 measured the same). Models with more states get
    `SimError::TooManyStates`. Results are unchanged: all tests pass with the same error figures.
- **The binding built a new Rayon pool on every call.** Pools are now cached per thread count.
- **Accuracy note:** the max relative error of Rust/Numba (1.4e-6 at N=1e4, 1.8e-6 at N=1e5) exceeds rtol = 1e-6. That is expected,
  because rtol bounds the local error per step, not the global error. SciPy RK45 reached 1.0e-6 on its 2000-subject subset.
  Matching *measured* accuracy, as the brief section 7.1 asks, is a job for M4: tune each tool to the same achieved error.
- **Decision: go.** At equal tolerances Rust is at least as fast as the Numba port, single- and multi-threaded, and has no JIT
  warm-up (Numba: 0.9–1.0 s per process). It is far faster than the SciPy loop. For this *linear* model the vectorised NumPy closed form is faster than Rust
  on one thread, as the brief predicted. The case for the Rust simulator rests on the nonlinear models (M2), which have no closed form.

## 2026-11-06: M2 nonlinear models and benchmark
- `twocmt_mm_iv` has parameters (Vmax mg/day, Km mg/L, V1, Q, V2). `twocmt_iv_idr` reuses the `twocmt_iv` RHS for its PK part and adds
  `R` with `R(0) = 1` via `Model::init`. The output `p = R/(R + 9)` uses `IDR_R_REF = 9` (toy choice, 10 % baseline).
- **No clamping of negative amounts.** Near-zero amounts can dip below 0 by less than `atol` (observed −1.2e-14 mg), so the tests
  assert `≥ −atol`. Clamping would change the integrator. The limitation is documented in `docs/models.md`.
- **Property-test noise floor.** The MM comparison property `C(kD) ≥ k·C(D)` is only checked where `k·C(D) > 1e-8 × peak`.
  A proptest counterexample showed values of 4e-13 vs 2e-12 mg/L, which is solver noise at the absolute tolerance, not a model error.
  The regression file is committed.
- **Nonlinear references** come from SciPy DOP853 at rtol 1e-12, stopping at every event and output time (no interpolation).
  pytest runs them, so the reference stays independent of the Rust code.
- **Benchmark (`benchmarks/bench_nonlinear.py` → `results/bench_nonlinear.json`, git 263bd78):** each tool is tuned to the loosest
  rtol on a 4-per-decade grid (atol = 1e-3·rtol) whose *achieved* max relative error on 2000 subjects is ≤ 1e-6, measured against cytopk at
  rtol 1e-12 / atol 1e-15. The reference agrees with SciPy DOP853 to ≤ 1.8e-12. At N = 1e5 the measured error is 1.2–1.4e-6 for all
  tools, slightly above the target, because a larger N means more chances for a worst case. Reported as measured.
- **Result:** Rust and the same-algorithm Numba kernel are within about ±10 % on the MM model; Numba is 1.07–1.12× faster single-threaded on
  IDR; Rust is 1.07–1.22× faster with 16 threads. I did not profile the single-threaded IDR gap: it is small and the conclusion doesn't
  depend on it. JAX + diffrax on CPU (untuned, `vmap` in lockstep) was 2.3–9.9× slower than single-threaded Rust and slower with
  16 threads than with 1. The load average at start was 3.3, from the preceding smoke run, and is recorded in the JSON.

## 2026-11-06: SBI-flow benchmarks (benchmarks/sbi_flow/)
- **Decision rules were committed before measuring** (b3ecf04). Verdicts and all tables are in `benchmarks/sbi_flow/README.md`.
  The tables are generated from the JSON by `make_tables.py`, so nothing is typed in by hand.
- **Separate environment `.venv-sbi`** (BayesFlow 2.1.0, Keras 3.15.1, JAX 0.12.0.1 with CUDA 13 wheels) so the GPU-enabled JAX
  cannot silently change the earlier CPU-only benchmark environment. The RTX 5060 Ti (compute capability 12.0) works with
  `jax[cuda13]` on driver 580. GPU runs need `JAX_PLATFORMS=cuda,cpu`, because BayesFlow's logging uses a CPU device callback.
- **Small-batch fix (E2).** `n_threads=1` paid ~9 µs per call, even for zero simulations, handing the call to a cached
  1-thread Rayon pool. That is about one whole simulation. `n_threads=1`, and any batch below `MIN_PARALLEL_BATCH = 4`, now run on the
  calling thread (`Parallelism::Serial`, new `simulate_batch_with`). Batch-1 latency fell from 20.3 to 9.9 µs. Results are bit-identical
  in both modes (tested). The threshold of 4 is the smallest batch at which the 16-thread path already beat a single thread in
  the before-fix sweep (31 vs 86 µs at batch 8). Below that, the hand-off cost is comparable to the work.
- **Interleaved measurement for fast simulators (E1).** Running Numba and cytopk in separate processes gave a 19.65 vs 3.97 ms
  difference at B = 2048 that did not reproduce. Once JAX is loaded, per-call times vary a lot between processes and over time.
  Measuring both in one BayesFlow process, round-robin over 80 rounds, removes that confound.
- **In-process slowdown: cause found, and it is not JAX** (`benchmarks/sbi_flow/jax_slowdown.py`).
  - E1's 5.3× slower ODE call comes from the idle gaps between calls, not from JAX. Importing, initialising and
    running JAX changes nothing. NumPy work or a ≥ 1 ms sleep between calls reproduces the slowdown without JAX.
  - Controlled single-core test: a sleeping gap drops CPU 0 to 800–1,782 MHz and slows calls 2.3–5.4×, while a
    spinning gap keeps 4,100+ MHz and leaves the call time unchanged. Machine: intel_pstate powersave, EPP `power`.
  - A busy main thread pinned to one core keeps the pool fast; the reason is not shown.
  - The decisive EPP=performance check needs root and was not run.
  - E1 numbers are kept as measured under the default power settings.
- **DDM RNG.** I chose xoshiro256++ with SplitMix64 per-trial seeding and the Marsaglia polar method because the exact same algorithm can be
  written in Numba, which makes Rust-vs-Numba agreement a bit-for-bit check. Ziggurat would be faster but harder to replicate.
  The analytic check uses the Broadie–Glasserman–Kou discrete-monitoring correction, because the uncorrected formula is off
  by ~3× the tolerance at dt = 1 ms.
- **E4 not done.** BayesFlow 2.1's `DiskDataset` reads one pickle per simulation, so "10^7 simulations as shards" has no
  supported loader format.

## M5: FCS reader (cytopk-fcs)

- **Lenient by default, strict on request.**
  - Real files rarely conform. Strict mode reads 6/30 of the public test files
    (`benchmarks/results/fcs_robustness.json`).
  - Lenient mode repairs each known deviation and returns a typed warning, rather than printing or guessing
    silently.
- **Empty value vs escaped delimiter.** A doubled delimiter right after a keyword is an empty value; anywhere else
  it is an escape. The one legal case this misreads (a value that starts with the delimiter) is refused by the
  writer. See `docs/fcs_notes.md`.
- **DATA offset choice.**
  - **Bug found and fixed:** the first version clipped TEXT where the HEADER said DATA started. On FlowIO's
    `data_start_offset_discrepancy_example.fcs` that dropped `$BEGINDATA` and silently returned the wrong bytes;
    the cross-check against flowio caught it.
  - **Rule now:** never clip TEXT on the HEADER's word. Take the first range that lies inside the file, outside
    TEXT, and holds at least `$TOT` events, keywords before HEADER.
- **Integers become f64.** This is exact up to 53 bits and keeps one output type for D and I. The cost is the slow
  integer path measured in `fcs_speed.json`, where fcsparser wins on a 32-bit integer file; a typed integer output
  is a candidate for M6.
- **Values as stored.** `$PnE`/`$PnG` are not applied. FlowKit's "raw" applies `$TIMESTEP`, gain and log scaling, so
  cross-checks against FlowKit use only linear, gain-1, non-time channels.
- **Test material.**
  - **Bras & van der Velden (2020) set:** public on FlowRepository (FR-FCM-Z2LG), but downloading needs a CAPTCHA.
    The only API client ID belongs to FlowRepositoryR, so it is not used. `scripts/fetch_test_data.py
    --bras-archive` verifies and unpacks a hand-downloaded archive.
  - **Artificial corpus:** `benchmarks/fcs/corpus.py` covers the same deviation categories. It favours cytopk by
    construction, as `benchmarks/fcs/README.md` states.
  - **Real files:** 30 files from the flowio, FlowKit and fcsparser repositories, pinned by commit and SHA-256.
- **fcsparser 0.2.4 fails with NumPy 2** (`ndarray.newbyteorder`). It is benchmarked twice, in the shared NumPy 2.5
  environment and in a NumPy 1.26 one, so its column reflects the reader, not the NumPy version.
